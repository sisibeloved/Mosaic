# 1. 动机与范围

群聊至今只有纯文本。日常讨论需要把本地文件交给 agent 看（日志片段、截图、配置、代码文件）。
范围：**人类在聊天输入区上传本地文件，作为消息附件随消息发布；agent 侧按适配器能力注入语境**。
不在本 RFC 范围：agent 产出附件回传（执行产物面归 M4-1 执行生命周期）、云端/OSS 存储（本地单用户产品，无远端）、拖拽/粘贴上传之外的批量管理。

# 2. 语义设计

## 2.1 数据模型：附件描述子（attachment descriptor）

`message.posted` 载荷新增可选 `attachments` 数组（≤4 项/消息），每项封闭字段集：

```json
{
  "attachment_id": "att_<12hex>",        // 服务端生成（命令面不收，同 provenance 固化先例）
  "name": "build.log",                  // 原始文件名（basename 化，≤200 runes，控制字符剔除）
  "mime": "text/plain",                 // 探测值，未知为 application/octet-stream
  "size_bytes": 1024,                   // ≤ 单附件上限
  "storage_path": "rooms/<room_id>/attachments/<attachment_id>",  // 相对数据目录
  "sha256": "<hex>"                     // 完整性校验（导出/审计/去重）
}
```

- 命令面：`post_message` 载荷收 `attachments` 上传令牌列表（见 2.3 两步流程），服务端以令牌换取已落盘文件并固化描述子；直接内联 base64 不收（1MiB 命令体上限既有约束下不可行）。
- 事件面：`message.posted` 载荷携带固化后的描述子数组；删除房间级联清附件目录（M3-6 语义延伸）。

## 2.2 大小与数量上限（建议值，负责人可裁）

| 项 | 建议上限 | 理由 |
|---|---|---|
| 单附件 | 8 MiB | 文本注入摘录上限（2.4）远小于此；二进制走路径引用，8 MiB 覆盖常见日志/截图 |
| 每消息附件数 | 4 | 群聊语境注入的实用上界；更多走多条消息 |
| 每房间附件总量 | 512 MiB | 本地磁盘护栏；超限拒绝上传并指路清理（数据主权面 RFC-0010） |
| 文本注入摘录 | 每附件 8k runes | 语境膨胀护栏（codex 会话恢复本就带全量历史，注入摘录须有界） |

## 2.3 两步上传流程（先落盘、后发消息）

1. **上传**：`POST /v1/rooms/{room_id}/attachments`（multipart/form-data，单文件）→ 服务端流式落盘数据目录 `attachments/rooms/<room_id>/`（0600，目录 0700——数据面 owner-only 先例）→ 返回 `{token, name, mime, size_bytes, sha256}`。令牌为服务端生成的不可猜测 id，**有效期 24h、单次消费**（防上传面被当免费存储；过期未消费即清理）。
2. **发消息**：`post_message` 载荷 `attachments: [token…]` → 服务端按令牌定位文件、校验 sha256、重命名稳定化（`<attachment_id>` 定稿）、固化进事件载荷 → 令牌失效。

失败语义：令牌无效/过期/已消费 → `invalid_attachment` 400；sha256 不符 → 400（磁盘损坏显式暴露，不静默）。

## 2.4 组装注入策略（能力差异如实降级）

contextx 组装层新增 `attachments` 摘录段（注入在消息正文邻近，属既有 history 层）：

- **文本类**（mime text/*、application/json、xml、yaml、csv、markdown；或 UTF-8 可解码且无 NUL）：注入**头部摘录**（8k runes，标注 `[附件 name，共 N 字节，截断]`）——三家 CLI（codex exec / kimi -p / mcode exec --input）提示词均走 stdin，通道无碍。
- **图像**：按适配器能力标记——kimi 图像入参实证可用则注入路径+元数据并标注"可请求查看"；codex/mcode 当前无头 exec 不支持图像输入，注入 `[图像附件 name，W×H，agent 无法查看原图]` 如实降级。**能力标记由适配器 Capabilities 声明，不虚构**（同 HistoryChannel 先例）。
- **其余二进制**：注入 `[二进制附件 name，mime，size]` 路径与元数据；agent 经自身工具（web_fetch/文件读取）按工作目录策略访问——附件目录对 agent 工具只读暴露面**不在本 mini-RFC 实现**（涉及 OQ-20 边界与工作目录隔离，登记 M4-1 执行生命周期一并裁定），首版仅注入元数据。

## 2.5 SPA 交互（参考飞书）

输入区左侧回形针按钮 → 系统文件选择器 → 选中即上传（显示进度/失败重试）→ 输入区上方附件 chip（名称 + 大小，× 移除）→ 随消息发送。气泡内附件渲染为文件卡片（名称/大小/图标；点击经壳打开本地文件——web 形态复制路径）。agent 消息无附件（首版）。

# 3. 安全与隐私

- 上传端点过既有写门三件套（Origin / Content-Type multipart 含 boundary / X-Owner-Token）。
- 文件名 basename 化 + 控制字符剔除 + 不得以 `.` 开头（路径注入防御；storage_path 由服务端生成，不采信客户端路径）。
- DLP 发布门既有规则不适用于附件本体（不进正文流），但**文本摘录注入前过同款秘密形状剔除**（私钥块/bearer/sk- 前缀——用户可能上传含密钥的配置文件，注入语境即进入 CLI 会话）。
- 附件随房间删除级联清除（墓碑不保留内容，仅事件载荷中的描述子留痕）。

# 4. 兼容与迁移

- 旧客户端不发送 attachments 字段（可选字段，回放容错既有纪律）；旧事件无该字段投影为零值。
- 导出（NDJSON）包含事件载荷即包含描述子；附件文件本体导出为可选目录拷贝（备份面"副本即拷贝"语义覆盖，不单独立项）。

# 5. 开放问题（评审点）

- **OQ-1 附件对 agent 工具的只读暴露面**：**已裁定（负责人指令 2026-09-07："可以保存到临时文件夹传 PATH 给 Agent 吗"→ 落地为路径注入）**——语境注入附附件本体绝对路径（不复制临时文件：附件即稳定存储、hash 已校验、免一套临时生命周期）+ WSL `/mnt/<drive>` 视图（agent 座位在发行版内，Windows 盘符路径不可直达），agent 用自身文件工具按路径读全文/原图；图像能否被查看取决于各 CLI 工具能力（多模态文件读取则可见，否则字节），如实标注不虚构。安全口径：v1.52 全权限裁定下 agent 本就能读数据目录（同用户进程，位置隔离非强制隔离的既有登记不变）——路径注入不新增暴露面。
- **OQ-2 单附件上限 8 MiB 是否合适**：已按建议值实施；负责人实际使用形态（日志多大、截图多大）驱动调整，上限过低会逼用户手工截取。
- **OQ-3 令牌有效期 24h**：已按建议值实施；上传后长时间编辑消息草稿的场景是否需要更长？
